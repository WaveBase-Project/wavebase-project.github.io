Migrations generated from your Hibernate entities.

WaveBase brings the Entity Framework / Django workflow to the JVM. Change an @Entity, run one task, and get a versioned Migration with reviewable SQL for PostgreSQL, MySQL and H2. Gradle and Maven plugins included.

Five ideas to know

Everything WaveBase does is built on these. The full glossary ships with the source code.

Entity Model

The @Entity classes in your main source set, read via reflection after compilation.

Model Snapshot

A committed JSON file holding the last known Entity Model. The baseline every diff is computed against.

src/main/resources/db/model-snapshot.json

Migration

A versioned folder with plain SQL per dialect. A missing down.sql means it is irreversible on that dialect.

db/migration/<version>/postgresql.up.sql

Schema History Table

Lives in the database and records which Migrations are applied there. Created on first use.

wavebase_schema_history

Reverse Scaffold

One-shot generation of entity classes from an existing database, for onboarding legacy schemas.

Quickstart

WaveBase is not on Maven Central or the Gradle Plugin Portal yet. Until the first release, build it from a local checkout.

The source repository opens soon. It is still private while the first release is validated. The steps below show the setup as it will work once it is public. Follow the organization to be notified.

  1. Clone WaveBase next to your project

    git clone https://github.com/WaveBase-Project/WaveBase.git ../WaveBase

  2. Include the build and apply the plugin

    settings.gradle.kts
    pluginManagement {
    includeBuild("../WaveBase")
}
    build.gradle.kts
    import io.github.agallina.wavebase.core.dialect.Dialect

plugins {
    java
    id("io.github.agallina.wavebase")
}

dependencies {
    runtimeOnly("org.postgresql:postgresql:42.7.3")  // your JDBC driver
}

wavebase {
    jdbcUrl.set(providers.environmentVariable("WAVEBASE_JDBC_URL"))
    jdbcUsername.set(providers.environmentVariable("WAVEBASE_JDBC_USER"))
    jdbcPassword.set(providers.environmentVariable("WAVEBASE_JDBC_PASSWORD"))
    dialect.set(Dialect.POSTGRESQL)  // or MYSQL, H2
}

  3. Generate your first Migration

    With no snapshot yet, the first Migration creates every table, ordered so foreign keys come after the tables they reference.

    ./gradlew wavebaseGenerateMigration
# WaveBase: generated Migration 20261010143005123001 in src/main/resources/db/migration/...

  4. Review, commit, apply

    git add src/main/resources/db
git commit -m "Initial schema"
./gradlew wavebaseApply

  1. Build and install WaveBase locally

    Build the jars from a checkout, then install wavebase-core and wavebase-maven-plugin into your local repository with mvn install:install-file.

    git clone https://github.com/WaveBase-Project/WaveBase.git
cd WaveBase && ./gradlew :wavebase-core:jar :wavebase-maven-plugin:jar

  2. Add the plugin to your pom

    pom.xml
    <plugin>
  <groupId>io.github.agallina</groupId>
  <artifactId>wavebase-maven-plugin</artifactId>
  <version>0.1.0-SNAPSHOT</version>
  <configuration>
    <jdbcUrl>${env.WAVEBASE_JDBC_URL}</jdbcUrl>
    <jdbcUsername>${env.WAVEBASE_JDBC_USER}</jdbcUsername>
    <jdbcPassword>${env.WAVEBASE_JDBC_PASSWORD}</jdbcPassword>
    <dialect>POSTGRESQL</dialect>
  </configuration>
  <executions>
    <execution>
      <goals><goal>verify-migrations</goal></goals>  <!-- runs in the verify phase -->
    </execution>
  </executions>
</plugin>

  3. Generate, review, apply

    mvn compile wavebase:generate-migration
git add src/main/resources/db && git commit -m "Initial schema"
mvn wavebase:apply

Workflows

The everyday loop is the same for everyone. What differs is who runs the SQL against the database.

The everyday loop

// 1. change an entity
@Entity @Table(name = "posts")
public class Post {
    @Id private Long id;
    @Column(nullable = false) private String title;
    @Column private String summary;            // new
    @ManyToOne(optional = false) @JoinColumn(name = "author_id")
    private User author;
}
# 2. generate: writes db/migration/<version>/ and updates model-snapshot.json
./gradlew wavebaseGenerateMigration

# 3. commit the entity, the Migration and the snapshot together
git add -A && git commit -m "Add Post.summary"

# 4. CI: `check` fails if someone forgets step 2
./gradlew check

Automatic apply

WaveBase runs the SQL itself. Good for local, test and most CI/CD environments.

./gradlew wavebaseApply
./gradlew wavebaseRevert            # last one
./gradlew wavebaseRevert --to <v>   # everything after <v>

DBA applies by hand

A DBA runs the generated SQL file; WaveBase only records it. Drift check confirms the result.

# DBA runs <v>/postgresql.up.sql
./gradlew wavebaseMarkApplied --version <v>
./gradlew wavebaseVerifySchema

Onboard an existing database

Reverse Scaffold writes one entity class per table. It runs once: after that, your entities are the source of truth.

./gradlew wavebaseReverseScaffold --package com.acme.entity
# review and commit the generated classes, then create the baseline:
./gradlew wavebaseGenerateMigration
./gradlew wavebaseMarkApplied --version <v>   # tables already exist
Renames are drop + add. v1 detects created/dropped tables, columns and foreign keys. A renamed column shows up as a drop followed by an add, which loses data. Always read the generated SQL before applying.

Command reference

The Gradle tasks (group wavebase) and the Maven goals behave identically.

GradleMavenDatabaseWhat it does
wavebaseGenerateMigrationwavebase:generate-migrationnoDiffs entities against the snapshot, writes a new Migration and updates the snapshot. No-op if nothing changed.
wavebaseVerifyMigrationswavebase:verify-migrationsnoFails if entities changed without a Migration. Wired into check / verify. Disable with wavebase.verify.enabled=false.
wavebaseApplywavebase:applywritesRuns <dialect>.up.sql of every pending Migration, in order.
wavebaseRevert [--to v]wavebase:revert [-Dwavebase.to=v]writesReverts the last Migration, or every one after v. Fails if one is irreversible.
wavebaseMarkApplied --version vwavebase:mark-applied -Dwavebase.version=vwritesRecords v as applied, without running SQL.
wavebaseMarkReverted --version vwavebase:mark-reverted -Dwavebase.version=vwritesRemoves v from the history table, without running SQL.
wavebaseVerifySchemawavebase:verify-schemareadsCompares the live schema with the snapshot and fails on drift. Never auto-fixes.
wavebaseReverseScaffold --package pwavebase:reverse-scaffold -Dwavebase.package=preadsGenerates entity classes from an existing database.

Using WaveBase with an AI coding agent

Point your agent at llms.txt: a single plain-text file with the concepts, every command, the defaults and the rules below. Or paste this into your project's AGENTS.md / CLAUDE.md:

## Database schema (WaveBase)
Full reference: https://wavebase-project.github.io/llms.txt

- Entities under src/main/java are the source of truth for the schema.
- After changing any @Entity, run `./gradlew wavebaseGenerateMigration` and commit
  the new db/migration/<version>/ folder and db/model-snapshot.json together
  with the entity change.
- Never hand-edit model-snapshot.json or existing Migration folders.
- Read the generated *.up.sql / *.down.sql. Call out DROP TABLE / DROP COLUMN.
- Do not run wavebaseApply, wavebaseRevert, wavebaseMarkApplied or
  wavebaseMarkReverted against shared or production databases without approval.
- If `check` fails on wavebaseVerifyMigrations, generate the missing Migration;
  do not disable the check.
- If wavebaseVerifySchema reports drift, report it; do not edit the snapshot.
  • Deterministic, file-based output. Everything an agent produces is a plain file in the repo, reviewable in a pull request.
  • Safe by default. Generating and verifying never touch the database; only explicitly-named tasks do.
  • Loud failures. Missing Migrations and drift fail the build with a message naming the cause, so agents can self-correct.

Scope and status

Supported now

Java 17+, Hibernate 6 / Jakarta Persistence. PostgreSQL, MySQL, H2. Tables, columns, foreign keys. Gradle and Maven.

Not yet

Rename detection, indexes and unique constraints as separate changes, a standalone CLI, published artifacts.

Out of scope

NoSQL databases (planned as a separate project). Continuous sync from the database back to entities.
